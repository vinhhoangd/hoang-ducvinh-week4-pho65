## Part 3 — Required failure conditions (Step 7)

### Failure A — Unknown code

- **Prediction:** a correctly formatted but unregistered code shows an "unknown" page, creates no item, and writes no ledger row.
- **Trigger:** `GET /inventory/lookup?code=PHO65-INV-999001`
- **Observed:**
  ```text
  Unknown code
  PHO65-INV-999001 is not in Pho65 inventory. Nothing was recorded.
  Safe next steps: check the label for a typo, look up the item by name on the inventory list,
  or create the internal item if it is genuinely new.
  ```
- **State check:** item count unchanged; no transaction added.
- **Recovery:** none needed — the safe next action is offered as a link.
- **Repeat:** same result. **PASS**

### Failure B — Duplicate request

- **Prediction:** re-submitting a used request ID is refused; quantity and ledger row count change only once.
- **Trigger:** submitted a transaction on item 1 reusing request ID `r-03`; also `docker compose exec app python test_inventory.py`.
- **Observed message:**
  ```text
  That button press was already recorded; no duplicate transaction was added.
  ```
- **State after:** `8 bag, avg $2.25, value $18.00, ledger rows=3` — identical to before.
- **Which assertion proves it** (`test_inventory.py`): after three good events, the test calls `add_transaction(..., "r3")` a second time inside a `try`. It requires a `ValueError` containing `"already recorded"`; if the write had succeeded, the `else:` branch raises `AssertionError("duplicate request was accepted")`. The guard is the `request_id TEXT NOT NULL UNIQUE` column, so the database refuses the second write even if the interface is bypassed.
- **Test output:** `inventory known-answer and guard tests passed`
- **Repeat:** same result. **PASS**

### Failure C — Negative stock

- **Prediction:** using more than is on hand is refused whole; quantity unchanged; no row added.
- **Trigger 1:** with 8 bags on hand, submit `used` 100.
- **Observed message:**
  ```text
  This would make stock negative. Count what is present or record a correction with an explanation.
  ```
- **State after:** `8 bag, avg $2.25, value $18.00, ledger rows=3` — unchanged.
- **Trigger 2 (gap we found and fixed):** the starter guarded only `used`/`wasted`, so a negative `correction` or `counted` could still drive stock below zero. We extended the guard to every reducing action (`decision-table.md`, P6) and retested with `correction −999`:
  ```text
  This would make stock negative. Count what is present or record a correction with an explanation.
  ```
  State after: unchanged at 8 bags, 3 rows. **PASS**
- **Automated:** `test_inventory.py` asserts a `ValueError` containing `"negative"` for `used −100`.
- **Repeat:** same result both ways. **PASS**

### Failure D — Changing receipt cost

- **Prediction:** after receiving 10 at $2.00 and 10 at $2.50, a correct moving weighted average reports **$2.25**; a naive "latest price wins" implementation would report $2.50.
- **Trigger:** the Step 3 known-answer sequence (`r-01`, `r-02`, `r-03`).
- **Observed:** `8 bag on hand · average $2.25 · value $18.00` — matches the hand calculation; the $2.50 failure mode did **not** occur.
- **Recovery:** none needed, no bug found here.
- **Repeat:** the packaged test reproduces the same 8 / 225 / 1800 result. **PASS**

### Failure E — Denied camera

- **Prediction:** with camera permission denied, the page explains the problem, does not trap the worker, and the same item can still be identified by saved image or by typing the code.
- **Interface behaviour built for this:** the camera is requested only after the **Start camera** button; if `getUserMedia` fails or is denied, the page shows
  "Camera unavailable (…). Use the saved-image or typed-code path below — both work without the camera."
  and both alternative paths remain on screen.
- **Desktop check:** manual entry resolves the same item with no camera involved. **PASS (partial)**
- **Phone check with permission actually denied:** pending Step 8, recorded in `mobile-transfer-test.md`.

### Failure F — Low-stock boundary

- **Documented policy:** an item is LOW when `quantity <= reorder_point`. The rule is printed on the dashboard so the policy and the code cannot drift apart.
- **Prediction:** with a low-stock point of 2 — 3 on hand = OK, 2 = LOW, 1 = LOW.
- **Trigger:** Limes (`PHO65-INV-000103`, low point 2), set to each quantity with a signed `counted` adjustment.
- **Observed:**
  ```text
  on hand 3 (one above threshold 2): OK
  on hand 2 (exactly at threshold 2): LOW
  on hand 1 (one below threshold 2): LOW
  ```
- **Comparison used by the implementation:** `state["quantity"] <= row["reorder_point"]` — matches the written policy, so no fix was required.
- **Repeat:** same result. **PASS**

### Extra: waste and correction require a written reason

- **Prediction:** a WASTE with an empty note is refused and adds no row.
- **Observed message:**

- **State after:** unchanged (3 each, 3 rows). Re-submitting with the reason "dropped on floor" recorded exactly one row and left 4 each. **PASS**

### Extra: removing an item never destroys its history

- **Prediction:** an item that has recorded events cannot be deleted; an item with no events can be, because there is nothing to lose.
- **Trigger (2026-09-23):** pressed Remove on Viet BBQ (7 ledger rows) and on Limes (5 ledger rows).
- **Observed:**
  ```text
  Archived Viet BBQ. Its 7 ledger rows are kept — open 'Removed items' to restore it.
  Archived Limes. Its 5 ledger rows are kept — open 'Removed items' to restore it.
  ```
  Both disappeared from the working list and appeared under "Removed items". Opening the archived Limes still showed all 5 rows (`received`, `wasted`, `correction`, two `counted`).
- **Recovery:** pressed Restore; Limes returned to the list with its history unchanged.
- **Why it matters:** deleting the item would have orphaned its transactions, and the ledger could no longer explain how the count was reached. See `decision-table.md` P8 → P16. **PASS**
